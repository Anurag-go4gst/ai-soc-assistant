Meeting script read first

The 60-second walkthrough for a leadership or customer demo. Say this top-to-bottom; every claim below is backed by a section in this guide.

1

“Start with the user query. The live hop sequence is: user query → bootstrap (query understanding plus the canonical planning seam) → route resolution → parallel specialist fan-out (Skill, Knowledge, MCP, SPL) → fan-in merge into one validated work bundle → exactly one dispatch path → the governance chain → the final analyst response (1, 2). This is a governed agentic flow: specialists and LLM sidecars propose; policy gates approve anything sensitive — SPL execution, MCP access, MITRE status, severity. Response notes show Orchestration: resource_planner_hierarchy.”

2

“Query Understanding matches the query against the 105 taxonomy and the use-case catalog, and that match becomes a tier and a processing lane — T1/T2/T3 go down the known lane and T4 goes guided. T4 alone can then be re-tiered: a T4 turn that turns out to be a pure reference question resolves to T0 and short-circuits to governed knowledge (4). Unsafe containment requests are blocked to human review and never enter guided mode.”

3

“Both runtimes call one canonical planning seam, run_canonical_planning. There is no flag that turns it off, and no second copy of the routing/intent/planning logic to drift against — a static architecture guard fails the build if a fork reappears (3).”

4

“When a known question is missing a detail the system can look up itself, guided detail tools resolve it instead of interrupting the analyst — bounded to three calls and two iterations, read-only, deterministic selection, no LLM in the loop. Only details that genuinely need a human become a clarification, and that clarification is now a durable handoff the next turn resumes (5, 6).”

5

“MCP is governed at a gate, not by hope. Only an approved normalized_spl is admitted; candidate SPL is never executable; tool selection is deterministic and read-only discovery is separated from search; every call carries analyst confirmation. Blocked or skipped steps stay in the plan as honest lineage (9).”

6

“Finalize builds the analyst response card — not raw LLM prose (22) — and every turn leaves a durable trail: 28 catalogued planning events, PostgreSQL handoffs, and a two-phase response validation that refuses to emit a completion event for an answer that failed validation (11).”

One-line close: “The specialists and the model make it adaptive; the contracts and gates make it safe. Severity, MITRE, SPL execution, and MCP never leave controlled approval gates.”

1. The complete traversal rebuilt

Seven reader-level stages on every live /chat request. Routing, intent, completeness, detail resolution, and evidence planning are shown as one stage because they are literally one function — the canonical planning seam described in 3.

1

User query

Analyst asks a SOC question in natural language. Session context can rewrite a follow-up into an effective query and carries pinned entities, use case, and any pending clarification handoff.

2

Understand + recognise

The query is matched against the 105 taxonomy and the use-case catalog. This produces exactly one deterministic_match_path, which the lane router turns into a catalogue tier and a processing lane. Parse failure degrades to keyword failover — never an error.

3

Canonical planning

One seam builds the whole turn contract: intent, completeness check, detail resolution where needed, route adjudication, route contract, evidence plan, and a committed resource plan. It ends in exactly one typed outcome.

4

Specialist fan-out

The plan already exists. Four specialists — Skill, Knowledge, MCP, SPL — report in parallel on catalogue tier, knowledge gaps, MCP posture, and SPL posture. They enrich; they do not re-plan.

5

Fan-in merge

Reports and the resource plan merge into one work bundle. Only a bundle that passes policy-parity validation becomes the validated_work_bundle that workers are allowed to read.

6

Dispatch

Exactly one path: RAG-only, composed plan, SPL workflow, or — for any non-planned outcome — straight to finalize with no route to execution at all.

7

Governance + answer

SPL validation, MCP execution gate, context sufficiency, facts and severity, answer guard, human review, policy veto, finalize, and a final-answer validation — then the analyst card and the durable trace.

Where the model appears: as an advisory route suggestion that must be registry-validated to win, as a detection-plan proposer whose JSON is compiled into SPL by deterministic code, and as an optional narrator of prose the facts do not depend on. Exact-105 turns commonly skip the advisory hops entirely.

3. The canonical planning seam new

The single most consequential change of the cutover. Routing, intent, completeness, detail resolution, and evidence planning used to exist twice — once in the imperative pipeline and once in the graph bootstrap. They are now one callable that both runtimes must use.

One entry, no flag

run_canonical_planning(state) in canonical_planning_orchestrator.py. is_canonical_authoritative() returns a hard-coded true — there is no canonical feature flag left to misconfigure.

Fork detection is a test

A static architecture guard walks the AST and the graph edges to prove neither runtime holds its own routing, completeness, intent, or planning logic. It includes a negative control that must fail when a fork is deliberately reintroduced.

Typed exit, always

Every path out of the seam is a CanonicalPlanningOutcome. A database failure becomes persistence_failed, not a half-planned turn that renders as a confident answer. Before run_canonical_planning returns, enforce_canonical_outcome_invariant rejects missing, malformed, or cross-state contradictory artifacts and strips stale evidence_plan / execution eligibility.

Four sub-stages, in order

Node names in full: graph_node_lane_and_canonical_planning (ends with enforce_canonical_outcome_invariant) → graph_node_route_resolution → graph_node_route_contract → _graph_node_planning_decision_from_canonical.

Plan authority is enforced, not agreed. plan_evidence_from_canonical is the sole creator and committer of a ResourcePlan. Composition happens inside an authority context manager, and guided dispatch, the executor, the response composer, and telemetry may only deserialize and read. Static guards pin it.
Idempotency: if a handoff version already committed a plan, the seam replays the committed plan instead of composing a second one. A retried or duplicated turn cannot produce two different plans for the same handoff.

5. Guided detail tools new

The subsystem this cutover is named after. It exists to close one specific failure: a known catalogue question missing a single lookup-able field used to either divert wholesale into guided rescue — losing its governed SPL template — or bounce back to the analyst asking for something the system could find itself.

Stage 1 — the completeness gate

Every missing field is classified before anything is attempted. The classification, not a heuristic, decides what happens next.

CategoryFieldsConsequence
tool_discoverableindex, sourcetype, src, source_ip, host, domain, reference_datasetResolved by a detail tool. The analyst is never asked.
user_onlyalert_id, time_window, user, approval, analyst_confirmationBecomes a clarification. Only a human knows these.
planner_requiredeverything elseThe planner must supply it, or the turn degrades honestly.
optional—Recorded; never blocks.
An anti-over-asking rule. On a mapped catalogue use case with no concrete scoping entity in the query, missing fields are advisory only — they never divert the turn and never raise a clarification. Asking a broad question should not trigger an interrogation.

Stage 2 — selection

Deterministic, driven by intent family, answer goal, and the missing categories. No LLM participates in selecting a tool. An unsafe request selects nothing at all — the tool list returns empty and the turn is blocked, not resolved.

Stage 3 — bounded resolution

Hard budgets

MAX_TOOL_CALLS = 3, MAX_ITERATIONS = 2. Exceeding either appends an explicit limitation rather than silently continuing.

Typed error classes

Retryable: timeout, source_unavailable, transient. Fatal: policy_blocked, unsupported_source, auth_denied — a fatal error returns immediately and asks the analyst.

No plan authority

Resolution emits a GapResolutionResult and never a ResourcePlan. Filling a blank is not the same act as deciding what the turn will do.

The tools themselves

ToolStatus in this stageBehaviour
knowledge_recallexecutesGoverned reference-registry lookup returning typed facts and citations. It makes no live-environment claim. With no resolvable reference ids it returns partial and states the limitation instead of inventing coverage.
spl_generationplanned_read_onlyRecorded intent. Realised by the final planner as a resource-plan step.
attack_discoveryplanned_read_onlyRecorded intent, deferred to the final planner.
alert_summaryplanned_read_onlyRecorded intent, deferred to the final planner.

Deferred tools carry the limitation <tool>_execution_deferred_to_final_planner, so the trace says plainly what was recorded versus what was run.

Stage 4 — merge with provenance

Tool output does not overwrite what is already known. It merges under a fixed source precedence, and disagreements are recorded rather than resolved silently:

user 5  >  live_telemetry 4  >  knowledge_recall 3  >  catalogue_default 2  =  detail_tool 2  >  model_inference 1

Every conflict becomes a FieldConflict with an explicit accepted_new or kept_existing resolution. Duplicate tool calls are hashed and blocked against a budget of one.

Stage 5 — re-gate

After resolution the gate runs again and produces the terminal status: complete, complete_with_limitations, clarification_required, policy_blocked, or resolution_failed.

What the analyst notices: fewer interruptions, because look-up-able gaps are closed without asking. Governed SPL survives on catalogue questions instead of being replaced by an ungoverned draft. Clarification is a first-class answer mode rather than a thin low-evidence answer. And a clarification answer now actually resumes the original turn.

6. Clarification and the handoff lifecycle new

A clarification is a durable, versioned record — not a conversational hope that the next message will be interpreted correctly. 

Turn 1   a user_only gap survives resolution
         → outcome  clarification_required
         → handoff persisted, version 1, status "awaiting_clarification"
         → pending_handoff_id pinned to the session
         → answer_contract.answer_mode = "clarification"
         → NO evidence_plan, NO resource_plan

Turn 2   session context finds the pin → handoff_resume
         → resume_clarification_handoff  (transactional, SELECT … FOR UPDATE, replay-aware)
         → original query and tier/lane restored
         → analyst answer merged, intent reconstructed
         → completeness gate re-run
         → handoff version 2, status "plan_committed" → an ordinary planned turn

Transactional resume

The row is locked for update, so two concurrent turns cannot both consume the same clarification and commit divergent plans.

Versioned, not overwritten

The handoff advances by version. The audit trail keeps what was asked, what was answered, and which plan the answer produced.

Contract-enforced emptiness

A clarification_required outcome is forbidden from carrying an evidence plan. The clarification and policy-blocked branches explicitly clear it before returning.

Branching on a typed status removes the entire class of bug — and the topology backs it up, because a non-planned status has no edge to execution.

7. Resource Planner hierarchy — the production spine

One production orchestration spine. Specialists propose; code workers execute; governance vetoes unsafe outcomes. Three runners collapsed into this one during the cutover.

One runner

routes_chat and routes_chat_stream call run_chat_via_resource_planner_graph. The analyst-visible note reads Orchestration: resource_planner_hierarchy. — there is no parity mode and no second full runner to fall into.

Parallel specialists

LangGraph Send fan-out across Skill, Knowledge, MCP, and SPL. Fan-in sorts the reports, merges them into a work bundle, runs validate_bundle_policy_parity(), and only then publishes validated_work_bundle.

Option A boundary

The plan exists before specialists run. They enrich args_template fields they own and nothing else. Route, intent, and evidence-plan authority stay deterministic and upstream.

Compiled topology: bootstrap → route_resolution → resource_planner_delegate → parallel specialists → resource_planner_merge → dispatch (non_planned_finalize / prepare_rag_only / composed_dispatch / workflow_spl) → source-resolve when needed → governance chain (spl_validate → mcp_execution_gate → context_sufficiency → decide_facts → answer_guard → human_review → policy_veto → finalize → validate_final_answer).

Fail loud, never silently

An unhandled defect on /chat returns a sanitized HTTP 500 with chat_pipeline_failed telemetry; the stream emits reporter.failed. A missing response uses the degraded facade, which is a guarded honest blocked card — it cannot re-enter the graph or recurse into a second pipeline.

What the specialists actually report

Skill reports the catalogue tier match. Knowledge runs a deterministic knowledge audit with no model involved. MCP and SPL report posture for the plan. Debug traces show the sequence as resource_planner.delegate → specialist.* → resource_planner.merge.

Dual-runtime parity at closure: total=120 exact=120 approved=0 critical=0 across the production corpus, up from 113 exact / 7 critical before the shared seam landed. 9. SPL generation and the MCP execution gate

MCP is attached. What follows is the governance around it — how a query becomes an approved statement, and what has to be true before that statement is allowed to run.

The candidate ladder

Tried in order, first success wins:

analyst-provided SPL
  → T2 native profile
  → governed catalogue template          ← preferred; carries template governance
  → deterministic lab draft
  → LLM plan-compiler failover           ← relevance-gated, grounded
  → clarification                        ← when nothing is defensible

The model proposes a plan, not SPL

On the failover rung the model emits a small JSON detection plan. Deterministic code compiles the SOC-STD SPL from it, and the result flows through the ordinary validation, quality, and adapter gates. Raw model SPL is never authority.

Slots must resolve

Index, sourcetype, and field placeholders are substituted from the source-profile map, SOC-KB retrieval, and session pins. Fully resolved becomes normalized_spl. Unresolved slots raise an analyst clarification — never a guess, and never a downgrade to an ungoverned draft.

Candidate ≠ executable

The raw candidate envelope stays approved=false / normalized_spl=null / execution_eligible=false. Only a separate derived artifact can become eligible, and only after normalization, real validation, slot resolution, and risk classification.

What the gate requires

ControlRule
AdmissionOnly an approved normalized_spl, or already-populated composed execution results, may enter.
Tool policyDeterministic selection. The search tool and read-only discovery tools are selectable for a search; write, admin, and assistant-style tools are not selectable at all.
User requestsA requested server or tool is a preference, never an instruction. Policy decides.
Analyst confirmationPer-call handshake — confirm, update_spl, or reject. An updated SPL re-runs source resolution before the gate sees it.
Risk classificationHigh risk — validator rejection, injection, risky command, missing time bounds or result cap — is blocked before the gate. Medium risk keeps confirmation. Auto-eligibility can only ever relax confirmation outside live registry mode; registry mode always confirms.
Search lifecycleSubmit → bounded poll → fetch, within explicit poll and timeout bounds. Outcomes are reported honestly as live, empty, timeout, or denied. An empty result is reported as empty, never padded.
After the factpolicy_veto re-asserts the plan's policy, so an execution the plan never authorised cannot survive to the answer.
Two independent axes for human-in-the-loop. Relaxing confirmation requires both a demo/lab execution mode and an explicit allowance flag. A single flag cannot switch off the analyst handshake — which is the point.

10. Canonical RunContract — one source of truth

Every live /chat turn builds a single RunContract / RouteContract in graph state. It ends the “competing truths” class of bug: the analyst card, the audit trace, the human-review gate, and the evidence counts all read from the same contract instead of re-deriving state per surface.

Single HIL truth

The capability gate, the governance trace, and the run contract project the same effective human-in-the-loop verdict. There is no second gate that can disagree with the first.

Honest evidence counts

The collected-evidence count comes only from telemetry that was actually collected. Collected, review-only, and candidate artifacts live in separate buckets, so the card cannot imply data it never fetched.

One route authority

Shadow comparisons are re-projected onto the canonical contract; the raw shadow is kept under a separate key for audit only, where it cannot leak into the answer as truth.

11. Persistence, idempotency, and telemetry new

The cutover moved planning state out of process memory. What a turn decided is now a durable, queryable record — which is what makes replay, resume, and audit possible at all.

PostgreSQL only

canonical_handoffs, canonical_planning_events, canonical_execution_idempotency. There is no memory or file fallback: if the database is unavailable the turn returns a typed persistence_failed outcome rather than pretending to have planned.

Migrations are a deploy step

Schema is applied by the container entrypoint, never as runtime DDL from a request path. /health exposes a migration readiness field so a half-migrated deployment is visible rather than mysterious.

Execution idempotency

A committed plan is keyed by handoff id and version. A retried turn replays the committed plan instead of composing a second, divergent one.

16. LLM usage — what the model may and may not do

The model is a participant, never an authority. Every hop it takes is a governed sidecar with a budget, a validator, and a deterministic floor to fall back to.

The model may

Suggest a route as an advisory that must be registry-validated to win. Propose a JSON detection plan that deterministic code compiles into SPL. Narrate analyst-summary prose. Assist with intent shaping on the rollback path. Every one of these is optional — a turn completes without it.

The model may not

Call MCP directly — the backend mediates every tool call. Decide severity or MITRE status. Make SPL executable. Approve its own output. Bypass human review. Produce a final figure or a fact that deterministic code did not establish.

The governed sidecar lane

01 · RESOLVE

Failover chain

Role-scoped provider and model resolution with a defined fallback order. A role with no configured endpoint simply does not run.

02 · BUDGET

Per-turn ceiling

Per-turn ceiling from AI_SOC_LLM_TURN_DEADLINE_SECONDS (code default 75s, COE/VPS profile 210s) with a tighter T2 clamp when configured. Per-hop timeout and intent-advisor reserve are separate knobs. The budget opens at routing; every call is recorded against it, including turn-timing attribution segments (workstream E).

03 · GROUND

Grounded prompt

Prompts carry a grounding block assembled from governed facts and references. Grounding is advisory context — it never becomes authority.

04 · GUARD

Validate or drop

Role-specific schema validation with deterministic overrides forced on conflict. A response that fails validation is dropped, not repaired into the answer.

05 · MERGE / FALL BACK

Deterministic floor

Any failure, timeout, or empty result falls back to the governed non-LLM path. The analyst still gets a safe, complete response.
