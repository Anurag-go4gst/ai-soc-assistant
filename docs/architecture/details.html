How a SOC question becomes a governed answer

This is the only path a live question takes. One query enters, one deterministic spine of eight stages runs, one analyst card comes out. The model participates at three narrow points and is never the authority at any of them.

Read the spine below first. Everything after it is the same eight stages at higher resolution — nothing on this page describes a second or alternative architecture, and anything that is not live is quarantined in Appendix A1.

Recognition tiers T0–T4

How well the question was recognised. Decides the lane, not the answer.

Planning outcomes 1 of 8

Exactly one typed status. Only planned can reach execution.

Route skills 5

A closed enum. Exactly one skill owns a turn.

LLM authority None, anywhere

Advisory, proposer, narrator. Never severity, MITRE, SPL execution, or MCP.

The live pipeline · read top to bottom

What happens to a SOC question

The tier tells us how confidently the request was recognized. It does not choose the answer. Every planned route then passes through the same four specialist reports, validated merge, one dispatch branch, and final governance checks.

plain-language view
  1. 1

    Receive the question and conversation context

    Carry forward the analyst’s question, approved session details, and any answer to a clarification from the previous turn.

    Implementation: resolve_session_context
  2. 2

    Recognize what kind of SOC request this is

    Compare the question with governed questions and use cases. This assigns an initial recognition tier and a starting lane.

    T1–T3 · recognized request

    Use the known lane. T1 is an exact governed question, T2 a known use case, and T3 a close or semantic match.

    T4 · not confidently recognized

    Use the guided lane first. Stage 3 may resolve a pure reference question to T0; otherwise it stays T4.

    Implementation: understand_query → route_skill → lane_router
  3. 3

    Decide whether to plan, ask for information, or stop safely

    Check the request’s intent, required details, and policy boundaries. For an initial T4 reference question, ask one concrete question: “Can trusted reference material answer this completely without checking the live environment?”

    Yes · resolve T4 → T0

    Use the reference-only lane and plan a governed knowledge answer. This is deterministic—not an LLM decision.

    No · remain T4 guided

    Resolve safe, discoverable gaps; ask the analyst for anything only they can provide; otherwise state the limitations.

    Implementation: run_canonical_planning → one typed outcome O1–O8
  4. 4

    Run four independent reports in parallel

    The route and plan already exist. These specialists inspect their own area; none may replace the route, invent a new plan, call a live tool, or approve execution.

    Routing Contract Auditor

    Reports the selected work mode and tier so downstream work can be checked against the routing decision.

    specialist_skill · canonical-tier correction pending
    Knowledge Coverage Auditor

    Reports which governed knowledge domains can support the plan and which evidence gaps remain.

    specialist_knowledge · live deterministic audit
    MCP Readiness Auditor

    Target role: report safe connector and candidate-tool readiness for MCP steps already present in the plan.

    specialist_mcp · fixed marker today
    SPL Readiness Auditor

    Target role: report template, data-source, required-slot, and validation readiness without writing SPL.

    specialist_spl · fixed marker today
    Important distinction: these are post-plan auditors. They are not the Route Skill selected in Stage 2, the Knowledge Retrieval Worker used after dispatch, the SPL builder, or an MCP executor.
  5. 5

    Combine the reports without changing the approved plan

    Accept only permitted, fill-blank enrichment from each specialist. Reject conflicting or out-of-scope proposals and publish one validated work bundle.

    Implementation: resource_planner_merge → validate_bundle_policy_parity
  6. 6

    Choose exactly one work path

    D1–D4 are alternatives, not consecutive stages. The committed plan and typed outcome choose one.

    D1 · Knowledge only

    Retrieve governed reference or SOC knowledge. Open no SPL path.

    D2 · Composed plan

    Walk the approved plan steps in order and skip anything unavailable or forbidden.

    D3 · SPL workflow

    Prepare a search candidate, validate it, bind the source, and apply the MCP execution gate.

    D4 · Stop or ask

    Finalize a clarification, policy block, or typed failure with no execution route.

    Runtime routes: rag_only · composed_dispatch · workflow_spl · non_planned_finalize
  7. 7

    Run only the workers authorized by the chosen path

    Knowledge Retrieval Worker

    D1 fetches governed knowledge with citations. This worker retrieves evidence; the Stage 4 knowledge specialist only audited coverage.

    Safe search and execution gates

    D3 prepares and validates SPL, resolves its data source, and requires the deterministic MCP gate before any execution.

    D2 may run several approved workers in plan order. D4 runs no evidence or execution worker.

  8. 8

    Check what the answer is allowed to claim, then build the analyst card

    Verify candidate safety and execution posture, check whether evidence is sufficient, constrain severity and MITRE claims, require human review when needed, re-apply plan policy, assemble the answer, and validate it again.

    Implementation: nine fixed governance nodes → analyst card + durable trace

These diagrams show only the steps each question actually takes. Both planned turns run the four specialist reports and validated merge. The recognition and work path differ; the safety boundary does not.

Path A · recognized request

T1–T3 → known lane → D3 search workflow

Example: “Which hosts are generating the most SMB traffic?”

  1. Receive the question. Carry forward safe session context.
  2. Recognize it as T1–T3. The question matches a governed question, use case, or close semantic form.
  3. Plan the answer. Confirm the attack-discovery intent and required evidence; commit one Resource Plan.
  4. Run all four specialist reports. Audit routing, knowledge coverage, MCP posture, and SPL posture without changing the plan.
  5. Validate the merge. Accept only permitted fill-blank enrichment.
  6. Choose D3. This example needs a governed search workflow.
  7. Prepare the search safely. Render or draft candidate SPL, validate it, bind its data source, and apply the MCP execution gate.
  8. Govern and present. Limit claims to evidence, apply human review where required, build the analyst card, and validate it.
Path B · reference resolution

Initial T4 → qualified T0 → D1 knowledge only

Example: “What is CVE-2024-3400?”

  1. Receive the question. Carry forward safe session context.
  2. Start at T4. No governed catalogue question matches the wording strongly enough.
  3. Qualify it as reference-only. Trusted reference material can answer completely; no live-estate check, correlation, or action is requested.
  4. Resolve T4 → T0 and plan D1. Commit a knowledge-only Resource Plan. T0 is deterministic, not an LLM classification.
  5. Run all four specialist reports. The same parallel fan-out occurs; no specialist may bypass or rewrite the plan.
  6. Validate the merge and choose D1. No SPL workflow opens.
  7. Use the Knowledge Retrieval Worker. Fetch governed reference facts and citations. This is different from the Stage 4 Knowledge Coverage Auditor.
  8. Govern and present. Prevent live-environment claims, build the cited analyst card, and validate it.
The invariant: T1–T3 and T4→T0 do not select different architectures. They enter the same Resource Planner, keep all four specialist lanes, merge under the same policy, choose one D1–D4 branch, and finish under the same governance chain.

Part I

The vocabulary

Four code systems appear throughout this page and in the trace. Learn these and the rest of the page reads itself. They are not interchangeable and they are not synonyms.

01 · TIERS

Catalogue tiers T0–T4 — how well the question was recognised

A tier is a statement about recognition strength, nothing else. It does not mean priority, severity, quality, or how much the LLM is used. It is derived from exactly one deterministic_match_path in Stage 2, in app/chat/lane_router.py.

Tierdeterministic_match_pathLaneWhat it means
T1 exact_105_question, exact_105_plus_use_case_catalog known Verbatim governed question. The strongest authority the system has — it pins the route, the answer shape, and the evidence contract.
T2 use_case_catalog known A known behaviour class from the 65-entry catalog, not an exact-105 question.
T3 near_105_question, semantic_105_question, fuzzy_alias_catalog known Recognised by token overlap, meaning, or a catalogue alias.
T4 out_of_registry, semantic_out_of_registry, query_understanding_weak, qu_unavailable, empty guided Novel or weakly understood. Guided resolution applies. The only tier that can still be re-tiered.
T0 none — no match path produces T0 knowledge_short_circuit Resolved reference. Assigned only inside Stage 3, only to a turn already tiered T4, when qualify_reference_query concludes the governed reference registry alone can answer it. Skill resolves to knowledge_recall.
Two tier fields, not one
initial_tier vs resolved_tier

Every turn carries both. initial_tier comes from the match path in Stage 2; resolved_tier is the value after qualification in Stage 3. For T1–T3 they are always equal. Only a T4 turn can end as initial_tier=T4, resolved_tier=T0.

A common misreading
T0 is earned, not detected

A bare CVE-… or T1059 in the query does not make a turn T0 on the live path. Qualification has to conclude the answer lives entirely in the governed reference registry.

The exact T4 → T0 rule

This is the decision people most often get wrong, so here it is with nothing left implicit. A T4 turn is re-tiered to T0 if and only if all four conditions hold (ReferenceQueryQualification.resolves_to_t0):

#ConditionWhat breaks it
1No action requested“remediate”, “patch now”, “block”, “contain”, “isolate”, “execute”, “run spl”
2No environment status check“are we affected”, “are our systems”, “check our”, “which devices”, “is it patched”, “vulnerable”, “exposure”, “affected by”
3No evidence correlation“was this observed”, “in alert”, “alert id”, “correlate”, “seen in our”
4Requested scopes are exactly {knowledge_only}Any second scope collapses the set to composite, which is not T0. An identifier alone, with no “what is / explain / define / describe” phrasing, is deliberately treated as ambiguous → composite → stays T4.

Pure definition questions

“What is CVE-2024-3400?” · “Explain T1059” · “What is AML.T0051”
→ scopes {knowledge_only}, no other marker → T0, lane knowledge_short_circuit, skill knowledge_recall, answer mode rag_only.

stays T4
Anything touching your estate

“Are we affected by CVE-2024-3400?” → environment status → guided.
“Hunt for T1059 in our estate” → investigation scope → guided.

The rule is substring matching on the raw query, and it is imprecise in both directions. A definitional question containing the word “vulnerable” is read as an environment status check and denied T0. It fails safe — it can only ever deny the short-circuit, never grant it — but do not read the marker lists as semantic understanding. The word “agentic”, precisely
Governed agentic, not autonomous

The system fans out, adapts, resolves its own gaps, and re-plans on resume — that part is genuinely agentic. What it never does is let a proposer be its own approver. Every sensitive act (SPL execution, MCP access, MITRE status, severity, containment) passes a deterministic gate.

Where the model actually appears
Three narrow points

(1) an advisory route suggestion that must be registry-validated to win; (2) a JSON detection plan that deterministic code compiles into SPL; (3) optional narration of prose that no fact depends on. Exact-105 turns commonly skip all three.

Part III

The flow in depth

The same eight stages, at implementation resolution. Section headers carry their stage number so you always know where you are on the spine.

06 · STAGES 1–2

Session context and query understanding

Effective query

Session context can rewrite a follow-up into a self-contained effective query, and carries pinned entities, use case, and any pending clarification handoff.

One match path

Matching against the 105 taxonomy and the use-case catalog produces exactly one deterministic_match_path, plus extracted entities and shape signals.

Degrades, never errors

If parsing fails the turn falls back to keyword failover (qu_unavailable → tier T4), which is a normal guided turn — not an exception.

The advisory route hop. The deterministic registry picks the primary route. An LLM route suggestion is consulted only when the registry does not retain authority, is normalized through the deterministic registries, and must be registry-validated to win. Final route selection is always deterministic.
07 · STAGE 3

The canonical planning seam

The single most consequential piece of the architecture. Routing, intent, completeness, detail resolution, and evidence planning used to exist twice — once in the imperative pipeline and once in the graph bootstrap. They are now one callable that both runtimes must use.

One entry, no flag

run_canonical_planning(state) in canonical_planning_orchestrator.py. is_canonical_authoritative() returns a hard-coded true — there is no canonical feature flag left to misconfigure.

Fork detection is a test

A static architecture guard walks the AST and the graph edges to prove neither runtime holds its own routing, completeness, intent, or planning logic. It ships with a negative control that must fail when a fork is deliberately reintroduced.

Typed exit, always

A database failure becomes persistence_failed, not a half-planned turn rendered as a confident answer. enforce_canonical_outcome_invariant tri-state-parses the outcome, checks cross-state consistency, strips stale evidence_plan and execution eligibility, and emits request.failed once.

The three boxes, in plain terms

These three names carry the whole design. Each one is doing a single job.

NameWhat it actually isWhy it exists
CanonicalPlanningInput
a data object		 A frozen, typed snapshot of everything the turn has decided so far — trace (ids, handoff, version), message (normalized query), routing (initial_tier, resolved_tier, lane, match path, primary skill, intent family, answer goal, use case), query_understanding (entities, signals, confidence, reference ids), detail_state (which fields are present, missing, and in which category, with per-field source and confidence), guided_resolution, and governance. Schema canonical_planning_input_v1. It is the only thing the final planner is allowed to read. Before this object existed, the planner reached into raw pipeline state and each runtime reached differently — which is precisely how the two runtimes drifted apart. Freeze the input, and the same input must produce the same plan everywhere.
plan_evidence_from_canonical
a function — the plan creator		 Five steps, in order: (1) ask the store whether this (handoff_id, handoff_version) already committed a plan — if yes, replay it and stop; (2) run plan_evidence() to get an EvidencePlan; (3) apply the canonical answer-mode override (clarification → clarification, knowledge_short_circuit or a reference/knowledge family → rag_only, SPL goals → live_investigation, guided → guided_investigation; otherwise leave the planner's own choice alone); (4) call compose_resource_plan inside resource_plan_authority(); (5) write the plan and the evidence plan to PostgreSQL and emit resource_plan.created. “Sole ResourcePlan creator” is literal. Composition only works inside that authority context manager, so no other module can quietly mint a plan. Guided dispatch, the executor, the response composer, and telemetry may deserialize and read — never create.

Step 3 is where a real bug was fixed: the override used to fall through to a catch-all live_investigation, which rewrote SOP and MITRE-explanation answers into live investigations and attached a lab SPL draft to a policy question.
enforce_canonical_outcome_invariant
a function — the exit gate		 Runs last, before anything downstream sees the outcome. (1) Tri-state read of the outcome — valid, absent, or malformed (absent and malformed are different bugs and are reported differently). (2) Cross-state consistency: does state agree with the status it claims? (3) Any inconsistency, absence, or malformation becomes a typed planning_failed instead of being passed along. (4) On any non-planned status it deletes evidence_plan, execution, and mcp_evidence from state. (5) Emits request.failed exactly once, never twice. The contract on the outcome object already forbids bad combinations (a clarification_required outcome carrying an evidence plan raises at construction). This gate defends the state around it. Without step 4, a turn that failed after partially planning could still carry a stale executable artifact into dispatch — and render as a confident answer.
Plan authority is enforced, not agreed. plan_evidence_from_canonical is the sole creator and committer of a ResourcePlan. Composition happens inside an authority context manager; guided dispatch, the executor, the response composer, and telemetry may only deserialize and read. Static guards pin it.
Idempotency. If a handoff version already committed a plan, the seam replays that plan instead of composing a second one. A retried or duplicated turn cannot produce two different plans for the same handoff.
08 · STAGE 3

Guided detail tools — closing gaps without interrogating the analyst

These exist to fix one specific failure: a known catalogue question missing a single lookup-able field used to either divert wholesale into guided rescue — losing its governed SPL template — or bounce back to the analyst asking for something the system could find itself.

Stage A — the completeness gate

Every missing field is classified before anything is attempted. The classification, not a heuristic, decides what happens next.

Stage B — selection

Deterministic, driven by intent family, answer goal, and the missing categories. No LLM participates in selecting a tool. An unsafe request selects nothing at all — the tool list returns empty and the turn is blocked, not resolved.

Stage C — bounded resolution

Hard budgets

MAX_TOOL_CALLS = 3, MAX_ITERATIONS = 2. Exceeding either appends an explicit limitation rather than silently continuing.

Typed error classes

Retryable: timeout, source_unavailable, transient. Fatal: policy_blocked, unsupported_source, auth_denied — a fatal error returns immediately and asks the analyst.

No plan authority

Resolution emits a GapResolutionResult and never a ResourcePlan. Filling a blank is not the same act as deciding what the turn will do.

Clarification is a first-class answer mode rather than a thin low-evidence answer. And a clarification answer actually resumes the original turn.
09 · STAGE 3

Clarification and the handoff lifecycle

A clarification is a durable, versioned record — not a conversational hope that the next message will be interpreted correctly.

Turn 1   a user_only gap survives resolution
         → outcome  clarification_required
         → handoff persisted, version 1, status "awaiting_clarification"
         → pending_handoff_id pinned to the session
         → answer_contract.answer_mode = "clarification"
         → NO evidence_plan, NO resource_plan

Turn 2   session context finds the pin → handoff_resume
         → resume_clarification_handoff  (transactional, SELECT … FOR UPDATE, replay-aware)
         → original query and tier/lane restored
         → analyst answer merged, intent reconstructed
         → completeness gate re-run

Transactional resume

The row is locked for update, so two concurrent turns cannot both consume the same clarification and commit divergent plans.

Versioned, not overwritten

The handoff advances by version. The audit trail keeps what was asked, what was answered, and which plan the answer produced.

Contract-enforced emptiness

A clarification_required outcome is forbidden from carrying an evidence plan. The clarification and policy-blocked branches explicitly clear it before returning.

11 · STAGE 6

Dispatch

Covered as a code system in section 4. The point worth repeating here is the topology guarantee.

D4 is structural. A turn whose Stage 3 outcome was not planned has no graph edge to SPL generation or to the MCP execution gate. It cannot reach execution even if a downstream check were buggy — the path does not exist in the compiled graph.

“What if the turn needs RAG and SPL and MCP?”

Then it takes D2. This is the most common misreading of the diagram, so it is worth being exact: “exactly one branch” describes the entry point, not the amount of work. The four branches are four scheduling strategies, and two of them run multiple kinds of work.

BranchChosen whenHow much work it can do
D1 rag_only evidence_plan.answer_mode == "rag_only" — checked first One kind. Governed SOC-KB retrieval. The execution stub is created already not-allowed, so no SPL or MCP lane is opened at all.
D2 composed_dispatch the committed ResourcePlan has steps — has_composed_plan(state) Many kinds, in plan order. This is the “all of the above” branch.
D3 workflow_spl everything else — the fallback SPL, plus a RAG hop when the plan asks for one. After SPL generation, _rp_after_workflow_spl routes into rag_early if needs_rag and rag_phase == "pre_mcp", then on to source resolve and the gate.
D4 non_planned_finalize Stage 3 status is not planned — checked before any of the above None. Straight to Stage 8.

So what is D2, concretely?

A composed plan is the committed ResourcePlan from Stage 3 expressed as an ordered list of steps, each bound to a registry resource and carrying a purpose. execute_plan_dispatch walks that list in order and dispatches every step whose purpose is dispatchable:

knowledge_retrieval spl_artifact mcp_execution cve_lookup mitre_mapping

The dispatcher reuses the same workers the other branches use — rag_early, workflow_spl, spl_source_resolve, execution, reference_finalize — so a composed turn that retrieves knowledge, drafts SPL, and calls MCP runs exactly the code D1 and D3 would have run, just scheduled from one plan instead of a fixed path.

Steps can be refused

A step bound to a blocked or not_onboarded registry resource is skipped before dispatch, with the reason recorded as lineage. Blocked work is visible, never silently dropped.

Commit is required

Dispatch refuses a plan whose provenance is not committed, and refuses a gap result with no plan — both become execution_failed rather than a partial run.

Idempotency guard

guard_plan_dispatch_idempotency runs before the walk, so a retried turn cannot dispatch the same side-effecting step twice.

Order of the checks matters. _rp_dispatch_route tests in this order: not-planned → D4; answer_mode == "rag_only" → D1; a composed plan exists → D2; otherwise → D3. So rag_only wins over a composed plan when both are present — a knowledge answer is never widened into an investigation by the presence of steps.

15 · DURABILITY

Planning state lives outside process memory. What a turn decided is a durable, queryable record — which is what makes replay, resume, and audit possible at all.

PostgreSQL only

canonical_handoffs, canonical_planning_events, canonical_execution_idempotency. No memory or file fallback: if the database is unavailable the turn returns persistence_failed rather than pretending to have planned.

A committed plan is keyed by handoff id and version. A retried turn replays the committed plan instead of composing a second, divergent one.

18 · LLM POLICY

What the model may and may not do

The model is a participant, never an authority. Every hop it takes is a governed sidecar with a budget, a validator, and a deterministic floor to fall back to.

The model may

Suggest a route as an advisory that must be registry-validated to win. Propose a JSON detection plan that deterministic code compiles into SPL. Narrate analyst-summary prose. Assist with intent shaping on the rollback path. Every one of these is optional — a turn completes without it.

The model may not

Call MCP directly — the backend mediates every tool call. Decide severity or MITRE status. Make SPL executable. Approve its own output. Bypass human review. Produce a final figure or fact that deterministic code did not establish.

The governed sidecar lane

01 · resolve
Failover chain

Role-scoped provider and model resolution with a defined fallback order. A role with no configured endpoint simply does not run.

02 · budget
Per-turn ceiling

AI_SOC_LLM_TURN_DEADLINE_SECONDS (code default 75s, COE/VPS profile 210s) with a tighter T2 clamp when configured. Per-hop timeout and intent-advisor reserve are separate knobs.

03 · ground
Grounded prompt

Prompts carry a grounding block assembled from governed facts and references. Grounding is advisory context — it never becomes authority.

04 · guard
Validate or drop

Role-specific schema validation with deterministic overrides forced on conflict. A response that fails validation is dropped, not repaired into the answer.

05 · merge / fall back
Deterministic floor

Any failure, timeout, or empty result falls back to the governed non-LLM path. The analyst still gets a safe, complete response.
